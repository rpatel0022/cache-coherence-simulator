\section{Problem Statement and Motivation}
% ============================================================

Cache coherence is a fundamental challenge in shared-memory multiprocessor systems~\cite{sorin2011primer}. When multiple processors maintain private caches over a shared address space, a coherence protocol must ensure that all processors observe a consistent view of memory. The three most widely studied snooping-based protocols---MSI, MESI~\cite{papamarcos1984mesi}, and MOESI~\cite{sweazey1986moesi}---each make different design tradeoffs between bus traffic, memory writebacks, and implementation complexity.

Despite their importance, these protocols are difficult to reason about from state transition diagrams alone. Students and practitioners must mentally simulate sequences of reads and writes across multiple processors, tracking state changes, bus messages, and data flow simultaneously. This cognitive burden makes it hard to build intuition for \emph{why} one protocol outperforms another in specific access patterns.

This project addresses that gap by building an \textbf{interactive, browser-based cache coherence simulator} that lets users step through memory traces operation-by-operation, observe state transitions in real time, and directly compare MSI, MESI, and MOESI side-by-side with quantitative metrics. Beyond visualization, we use the simulator to run a parametric study that characterizes \emph{when} and \emph{by how much} each protocol's optimizations matter as a function of workload sharing ratio.

\section{Background}
% ============================================================

\subsection{Snooping-Based Coherence}

In a snooping protocol, all caches monitor (snoop) a shared bus~\cite{stenstrom1990survey}. When a processor issues a memory operation that misses in its cache or requires exclusive access, it places a bus message (e.g., \texttt{BusRd}, \texttt{BusRdX}, \texttt{BusUpgr}) that other caches observe and react to by updating their local state. Correctness relies on the bus imposing a total order on all transactions, ensuring write serialization---every processor observes writes to the same block in the same order. Combined with the single-writer/multiple-reader (SWMR) invariant~\cite{sorin2011primer}, this guarantees coherence: at any point in time, either a single processor has read-write access to a block, or multiple processors have read-only access, but never both.

A key architectural implication is that simultaneous requests (e.g., two processors issuing \texttt{BusRdX} for the same block) are resolved by bus arbitration, which serializes them into a total order. This serialization is what makes snooping protocols simple but also fundamentally unscalable---every transaction must be visible to every cache, limiting the protocol to bus-based systems with moderate processor counts.

\subsection{Protocol Overview}

\textbf{MSI} is the baseline write-invalidate protocol with three states: Modified (M), Shared (S), and Invalid (I). Every read miss transitions to S, requiring a \texttt{BusUpgr} on any subsequent write. \textbf{MESI}~\cite{papamarcos1984mesi} adds the Exclusive (E) state, representing a clean, sole copy. A processor that reads a block with no other sharers enters E, allowing a silent upgrade to M on write with zero bus traffic. The E state requires hardware support: a shared-line signal on the bus that indicates whether other caches hold a copy. \textbf{MOESI}~\cite{sweazey1986moesi} further adds the Owned (O) state: when a modified block is read by another processor, the original holder transitions to O (retaining dirty responsibility and supplying data via cache-to-cache transfer) instead of writing back to memory.

A related variant is Intel's \textbf{MESIF} protocol, which adds a Forward (F) state. Like O, the F state designates a single cache to supply data on shared reads, but F applies to \emph{clean} blocks---avoiding redundant memory responses when multiple caches hold Shared copies. MESIF is designed for point-to-point interconnects rather than shared buses, and is outside the scope of this simulator.

\section{Approach and Implementation}
% ============================================================

\subsection{Architecture}

The simulator is implemented as a client-side web application in JavaScript, HTML, and CSS with no build step or server dependency---users simply open \texttt{index.html} in a browser. The architecture follows a clean separation of concerns:

\begin{itemize}[nosep]
  \item \textbf{Protocol layer}: A \texttt{BaseProtocol} class defines the snooping interface. \texttt{MSIProtocol}, \texttt{MESIProtocol}, and \texttt{MOESIProtocol} each implement \texttt{handleCpuRequest()}, encoding the full state machine for that protocol including bus message generation and snoop responses.
  \item \textbf{Simulator core}: The \texttt{Simulator} class manages per-processor caches, shared memory, and a \texttt{Metrics} tracker. It orchestrates each step: applying the requesting processor's transition, broadcasting snoop results to other caches, updating data values, and recording a full snapshot.
  \item \textbf{Trace parser}: Accepts a simple text format (\texttt{P0 R X}, \texttt{P1 W X 5}) with validation, comments, and error reporting.
  \item \textbf{UI layer}: Renders cache state grids, a bus log, step history table, and statistics panel with step-by-step execution, auto-run with adjustable speed, and a side-by-side protocol comparison mode.
\end{itemize}

\subsection{Implementation Decisions}

One non-obvious decision arose in the MOESI protocol when handling a \texttt{BusRdX} (write miss) directed at a block held in M state by another cache. The M holder must relinquish the block (M$\to$I) and supply data to the requester via cache-to-cache transfer. Critically, no writeback to memory is needed here: the dirty value transfers directly to the new M holder, who becomes responsible for eventually writing it back. Memory remains stale, but the SWMR invariant is maintained because exactly one cache holds the block in M at all times. This decision is correct for our model (unlimited cache, no eviction), but in a real system with finite caches, an eviction of the new M holder before writeback would require a memory update.

The simulator was validated by an automated test suite of 50 tests covering all state transitions, bus messages, snoop behavior, and data value propagation for all three protocols.

\section{Experimental Methodology}
% ============================================================

We conducted two sets of experiments. First, six hand-crafted microbenchmarks (Table~\ref{tab:traces}) isolate specific protocol mechanisms and serve as correctness checks against hand-derived state transitions from CS~213 Lecture~04~\cite{cs213lecture04}. Second, a \textbf{parametric sweep} over sharing ratio (0\%--100\%) with 500-operation randomly generated traces (4 processors, 8 blocks, 50/50 read/write mix, averaged over 5 runs) characterizes how protocol advantages scale with workload properties.

We define the \textbf{bus traffic} metric as follows: each bus request (\texttt{BusRd}, \texttt{BusRdX}, or \texttt{BusUpgr}) counts as one message, and each data supply response (whether from memory or cache-to-cache transfer) counts as one additional message. Thus a read miss that fetches data counts as 2 messages (request + response), while a \texttt{BusUpgr} counts as 1 (no data transfer). \textbf{Invalidations} count the number of cache lines invalidated by another processor's write. \textbf{Writebacks} count dirty-line writebacks to main memory.

The \emph{Silent Upgrade} trace demonstrates the E$\to$M mechanism: MSI produces 3 bus messages (BusRd request + data response + BusUpgr) while MESI produces 2 (BusRd request + data response, then silent E$\to$M). The \emph{Private Data} trace shows a 33\% bus traffic reduction (9 $\to$ 6) under MESI, arising from 3 read-write pairs each saving one \texttt{BusUpgr}.

Invalidation counts are identical across all three protocols for every trace, confirming the theoretical expectation: invalidations are a property of the write-invalidate approach, not of the specific state encoding. This serves as a correctness check on the implementation.

\textbf{MESI's bus advantage diminishes with sharing.} At 0\% sharing (fully private data), MESI reduces bus traffic by 20\% over MSI. As the sharing ratio increases, this advantage shrinks monotonically: 3.1\% at 20\%, 1.1\% at 60\%, and \textbf{vanishes entirely at 100\% sharing}. This is because the E state is only allocated when no other cache holds the block. As sharing increases, more reads find other sharers present, forcing the block into S instead of E and requiring a \texttt{BusUpgr} on subsequent writes --- exactly as MSI would. This quantifies a result that is qualitatively known but rarely measured: MESI's Exclusive optimization is \emph{only} effective for private-data access patterns.

\textbf{MOESI eliminates 100\% of writebacks at all sharing ratios.} Regardless of workload, MOESI produces zero writebacks while MSI and MESI produce writebacks that scale linearly with sharing (0 at 0\% sharing to 214 at 100\%). This confirms that the Owned state's benefit is orthogonal to sharing ratio: whenever a dirty block is read by another processor, the O state avoids the writeback regardless of how many shared accesses exist. As noted earlier, this is an upper bound --- real caches with eviction would trigger O$\to$I writebacks under cache pressure.

\subsection{Discussion}

The parametric results reveal a nuance not visible in small traces: the strict hierarchy MSI $\leq$ MESI $\leq$ MOESI holds across all sharing ratios, but the \emph{magnitude} of the gap varies dramatically. MESI's advantage is concentrated in private-data workloads and effectively disappears under heavy sharing, while MOESI's writeback elimination is uniformly beneficial. This explains the design choices of real processors: AMD uses MOESI~\cite{sweazey1986moesi} for its writeback savings across all workloads, while Intel adopted MESIF for efficient data forwarding on point-to-point interconnects where a designated supplier reduces redundant memory traffic.

\section{Conclusion and Lessons Learned}
% ============================================================

We built an interactive cache coherence protocol simulator and used it to conduct a parametric study across sharing ratios from 0\% to 100\%. The study quantifies two key findings: (1)~MESI's bus traffic advantage over MSI ranges from 20\% (fully private data) to 0\% (fully shared), diminishing monotonically with sharing ratio; (2)~MOESI eliminates 100\% of writebacks regardless of sharing ratio, though this is an upper bound due to our unlimited-cache model.

\textbf{Lessons learned:}
\begin{itemize}[nosep]
  \item Implementing the full state machines revealed subtleties not apparent from diagrams---particularly the MOESI \texttt{BusRdX} handling where a dirty block transfers cache-to-cache without a memory writeback, requiring careful reasoning about which cache holds the SWMR write permission at each step.
  \item The parametric sweep was more informative than hand-crafted traces: seeing MESI's advantage \emph{continuously} diminish from 20\% to 0\% across sharing ratios provided a quantitative understanding that individual traces could not.
  \item A 50-test correctness suite was essential. Several early bugs (e.g., incorrect \texttt{BusRdX} vs.\ \texttt{BusUpgr} selection, missing writeback on M$\to$I transitions) were only caught by systematic testing of all state$\times$operation combinations.
\end{itemize}

\textbf{Limitations and future work:} The simulator models a simplified single-level cache with unlimited capacity and no replacement policy. Extending it with set-associative caches and LRU eviction would allow studying the interaction between eviction-triggered writebacks and the O state's benefits. Adding directory-based protocols would address the scalability limitation of snooping, and incorporating memory consistency models (TSO, relaxed) would connect coherence to the broader memory system.
